# Sprint 02 計画案（M1：9枠を実在URLで埋める）

## 0. 決定事項（Q2〜Q5）- 仕様の一次ソース

このセクションはSprint 2の前提条件を確定したものです。P0-1〜P0-6の実装はこの決定事項に従います。

### Q2. 候補プール更新頻度
- **週1回目安、手動で更新する**
- 実行は GitHub Actions workflow_dispatch（手動実行）前提
- 自動スケジュール（cron）前提にはしない
- **理由**: 候補の鮮度と運用コストのバランスを考慮

### Q3. りなてぃ優先のトーン
- **主目的：食材プールから上手に使い切れる献立を立てる**
- りなてぃは「食材条件にヒットするなら優遇」くらい（主目的より強くしない）
- 実装上は同点/近似点のタイブレーク程度でOK（小さな加点など）
- **理由**: りなてぃは有用だが、食材使い切りが最優先

### Q4. 必須食材 / 食材プール（※同一概念として扱う）
- **「必須食材」と「食材プール」は同じものとして扱う**
- 生成時に食材プールを入力（1行1食材など簡易でOK）
- その中から最大2つまで must（今回だけ必須）指定できる
- mustは厳格制約にはしないが、候補がある限り最優先で反映
- 候補がない/反映できない場合は警告し、フォールバックで落とさない
- **理由**: シンプルな用語で混乱を避け、柔軟な運用を可能にする

### Q5. 共有/保存方針
- **食材プールは生成時に最新情報を棚卸して入力するため、保存/共有しない**
- Sprint2では端末間共有はやらない（将来共有するなら「設定のみ」が対象）
- 候補プールは端末側キャッシュOK（速度/安定目的）
- **理由**: 毎回最新の冷蔵庫状態で献立を立てるのが自然な使い方

## 1. Sprint Goal
外部ソース（白ごはん.com / Nadia / つくおき）から候補URLを取得し、
曜日ルール（水曜鯖・金曜スープ）を守ったまま、9枠を実在URLで埋める。

合格ライン：とにかく9枠がURLで埋まる（品質改善は次）

## 2. スコープ（In）
- URL候補取得（方式B）を実装し、候補プールを作る
- 9枠への割り当てロジックに候補プールを接続する
- 候補不足・取得失敗でも落ちない（警告＋フォールバック）
- キャッシュ導入（最低限）

## 3. スコープ外（Out）
- レシピ本文（材料・手順）の取り込み
- 買い出しリスト生成
- 自宅向け読み替え・分量換算
- Notion連携
- 過去レシピ検索
